# Adding a Load Balancer — Simple Summary

A **load balancer** distributes incoming requests across multiple backend servers instead of sending all traffic to a single server.

In **NGINX**, this is done by creating an **upstream** block that groups backend servers together. NGINX then forwards requests to this group using a load-balancing algorithm.

---

# Step 1: Create an Upstream Block

Edit the main NGINX configuration file:

```bash
sudo vi /etc/nginx/nginx.conf
```

Add an `upstream` block inside the `http` section.

Example:

```nginx
upstream nodebackend {
    server localhost:3000;
    server localhost:3001;
}

http {

    upstream nodebackend {
        server localhost:3000;
        server localhost:3001;
    }

    ...
}
```

You can also specify a load-balancing algorithm.

Example:

```nginx
upstream myservice {
    least_conn;

    server backend1.example.com;
    server backend2.example.com;
    server 192.0.0.1 backup;
}
```

### Explanation

* `upstream` creates a group of backend servers.
* `least_conn` tells NGINX to send requests to the server with the fewest active connections.
* If no algorithm is specified, NGINX uses **Round Robin** by default.
* `backup` marks a server that is only used if the primary servers become unavailable.

---

# Step 2: Update the Site Configuration

Modify your site's configuration to use the upstream group.

```nginx
server {

    ...

    location / {
        proxy_pass http://nodebackend;
    }

    ...
}
```

Instead of forwarding requests to one server, NGINX now forwards them to the entire upstream group.

---

# Step 3: Test and Restart NGINX

After making changes, verify the configuration.

```bash
sudo nginx -t && sudo service nginx restart
```

This checks the configuration for errors and restarts NGINX if everything is valid.

# Verifying Load Balancing

One way to verify that load balancing is working is by creating a custom log format that records which backend server handled each request.

---

## Step 1: Add a Custom Log Format

Inside the `http` block of `nginx.conf`:

```nginx
http {

    upstream nodebackend {
        server localhost:3000;
        server localhost:3001;
    }

    log_format upstreamlog '[$time_local] $remote_addr - $remote_user - $server_name $host to: $upstream_addr: $request $status upstream_response_time $upstream_response_time msec $msec request_time $request_time';

    ...
}
```

### Explanation

The custom log includes useful information such as:

* Client IP address.
* Requested URL.
* HTTP status code.
* Backend server (`$upstream_addr`) that handled the request.
* Response time.
* Total request time.

This makes it easy to confirm that requests are being distributed between servers.

---

## Step 2: Enable the Custom Access Log

Update your site's configuration.

```nginx
server {

    access_log /var/log/nginx/access.log upstreamlog;

    location / {
        proxy_pass http://nodebackend;
    }

}
```

This tells NGINX to write access logs using the custom `upstreamlog` format.

---

## Step 3: Test and Restart NGINX

```bash
sudo nginx -t && sudo service nginx restart
```

---

## Step 4: Monitor the Logs

View the access log in real time.

```bash
sudo tail -f /var/log/nginx/access.log
```

As requests arrive, you should see different backend servers (such as `localhost:3000` and `localhost:3001`) listed in the logs, confirming that load balancing is working.

# How Load Balancing Works

```text
             Clients
                │
                ▼
             NGINX
                │
      ┌─────────┴─────────┐
      ▼                   ▼
localhost:3000      localhost:3001
```

NGINX automatically chooses which backend server should handle each request.

---

# Load Balancing Algorithms

| Algorithm               | Description                                                                           |
| ----------------------- | ------------------------------------------------------------------------------------- |
| `Round Robin` (default) | Sends requests to each server in turn.                                                |
| `least_conn`            | Sends requests to the server with the fewest active connections.                      |
| `ip_hash`               | Routes the same client IP to the same backend server.                                 |
| `random`                | Selects a backend server randomly.                                                    |
| `least_time`            | Chooses the server with the fastest response time (available in some NGINX editions). |

# NGINX Keywords

| Keyword      | Purpose                                                        |
| ------------ | -------------------------------------------------------------- |
| `upstream`   | Defines a group of backend servers.                            |
| `server`     | Specifies a backend server in the upstream group.              |
| `backup`     | Marks a server as a backup, used only if primary servers fail. |
| `least_conn` | Uses the Least Connections load-balancing algorithm.           |
| `proxy_pass` | Forwards client requests to the upstream server group.         |
| `access_log` | Specifies where access logs are written.                       |
| `log_format` | Defines a custom format for log entries.                       |

---

# Key Points

* An **upstream** block groups multiple backend servers.
* NGINX uses the upstream group to distribute traffic across those servers.
* **Round Robin** is the default load-balancing algorithm.
* **least_conn** sends requests to the server with the fewest active connections.
* The `backup` directive defines a failover server.
* Always test the configuration with `sudo nginx -t` before restarting NGINX.
* A custom `log_format` combined with `access_log` allows you to verify that requests are being distributed correctly.
* Use `tail -f` to monitor access logs in real time.

---

# One-Sentence Summary

**Adding a load balancer in NGINX involves creating an `upstream` block to group backend servers, configuring `proxy_pass` to use that group, testing and restarting NGINX, and optionally using custom access logs to verify that requests are being distributed across the servers.**
