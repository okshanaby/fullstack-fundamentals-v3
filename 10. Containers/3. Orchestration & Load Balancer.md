# Orchestration & Load Balancer — Simple Summary

As applications grow, running a single container is no longer enough. You may have **dozens or hundreds of containers** that need to be deployed, monitored, updated, and scaled automatically.

This is where **container orchestration** and **load balancing** come in.

* **Container orchestration** manages containers.
* **Load balancing** distributes incoming traffic across containers or servers.

---

# Container Orchestration

**Container orchestration** is the process of automatically managing large numbers of containers.

It handles tasks such as:

* Deploying containers.
* Starting and stopping containers.
* Scaling containers up or down.
* Monitoring container health.
* Restarting failed containers.
* Rolling out application updates.

Instead of manually managing every container, an orchestration platform automates these tasks.

---

# How Container Orchestration Works

```text
Application
      │
      ▼
Container Orchestrator
      │
      ├── Start containers
      ├── Stop containers
      ├── Scale containers
      ├── Replace failed containers
      └── Update containers
```

# Load Balancer

A **load balancer** distributes incoming client requests across multiple servers or containers.

Instead of sending every request to one server, it spreads the workload so that no single server becomes overloaded.

Benefits include:

* Better performance.
* Higher availability.
* Improved reliability.
* Better resource utilization.
* Easier scaling.

---

# How Load Balancing Works

```text
               Clients
                  │
                  ▼
           Load Balancer
          ┌────┼────┐
          ▼    ▼    ▼
      Server 1 Server 2 Server 3
```

The load balancer decides which server should handle each request.

---

# Scheduling Algorithms

A **scheduling algorithm** determines how requests are distributed across servers.

## Round Robin (Default)

Requests are sent to each server in turn.

```text
Request 1 → Server A
Request 2 → Server B
Request 3 → Server C
Request 4 → Server A
```

**Best for:** Servers with similar capacity.

---

## IP Hashing

The client's IP address determines which server receives the request.

The same client is usually routed to the same server.

**Best for:** Applications requiring session consistency.

---

## Random Choice

Each request is sent to a randomly selected server.

**Best for:** Simple traffic distribution.

---

## Least Connections

The request goes to the server currently handling the fewest active connections.

**Best for:** Long-lived client connections.

---

## Least Load

The request is sent to the server with the lowest current workload.

This may consider factors such as:

* CPU usage
* Memory usage
* Current processing load

**Best for:** Dynamically balancing server resources.

# NGINX Upstream Configuration

An **NGINX upstream configuration** defines a group (cluster) of backend servers.

Instead of forwarding requests to a single server, NGINX can distribute requests across multiple servers using a chosen load-balancing algorithm.

Example:

```nginx
upstream backend {
    server 192.168.1.10:3000;
    server 192.168.1.11:3000;
    server 192.168.1.12:3000;
}

server {
    listen 80;

    location / {
        proxy_pass http://backend;
    }
}
```

In this example:

* `upstream` defines the backend server group.
* `proxy_pass` forwards requests to the group instead of a single server.
* NGINX automatically distributes requests among the servers.

# Monitoring Server Resources

The `htop` command provides a real-time view of system resource usage.

It shows:

* CPU usage.
* Memory usage.
* Running processes.
* System load.
* Process IDs.

Example:

```bash
htop
```

On macOS, the equivalent application is **Activity Monitor**.

---

# Commands

## Monitor System Resources

```bash
htop
```

**Explanation**

* `htop` – Opens an interactive system monitor that displays CPU usage, memory usage, running processes, and system load in real time.

---

# Command Flags

There are **no command flags** used in these notes.

The `htop` command is run without any flags.

# Key Points

* Container orchestration automates deploying, scaling, updating, and managing containers.
* Kubernetes is the most widely used container orchestration platform.
* A load balancer distributes incoming requests across multiple servers or containers.
* Load balancing improves performance, reliability, and scalability.
* Common scheduling algorithms include Round Robin, IP Hashing, Random Choice, Least Connections, and Least Load.
* NGINX uses **upstream** blocks to define groups of backend servers for load balancing.
* The `htop` command helps monitor CPU, memory, and running processes in real time.

# One-Sentence Summary

**Container orchestration automates the management of large numbers of containers, while load balancers distribute traffic across multiple servers using scheduling algorithms to improve performance, scalability, and reliability.**
