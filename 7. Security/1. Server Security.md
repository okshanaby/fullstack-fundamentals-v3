# Server Security — Simple Summary

This section explains the main risks when managing servers, why SSH keys are safer than passwords, how attackers behave, and basic security practices every server should follow.

---

# Key Security Risk (SSH Key Compromise)

If an unauthorized person gains access to a server that has an **SSH private key**, they can:

* Authenticate as that server on GitHub or other services
* Access private repositories
* Modify or steal company code
* Impersonate trusted systems

### Why this is serious:

The SSH key acts like a **master identity token** for the server.

So if stolen:

```text id="ssh-risk"
Server → SSH key stolen → Attacker = trusted user on GitHub
```

---

# Why Passwords Are Weak for Servers

Passwords are considered weak because:

* They can be guessed
* They can be brute-forced
* Users often reuse them
* They are vulnerable to automated attacks

### Comparison:

* Password → easy to attack
* SSH key → cryptographically secure

👉 SSH keys are significantly harder to break than passwords.

---

# Three Recommended Security Practices

## 1. Use SSH keys instead of passwords

* More secure authentication
* Prevents brute-force login attacks

---

## 2. Use firewalls

* Restrict who can access your server
* Only allow necessary ports (e.g. 80, 443, SSH)

Example idea:

* Block all traffic except trusted sources

---

## 3. Keep software updated

* Fixes security vulnerabilities
* Prevents exploitation of old bugs

```text id="update"
Old software = known vulnerabilities = easy target
```

---

# What to Do If a Server Is Compromised

If a machine is discovered to be hacked:

👉 **Standard recommendation: wipe and restore**

### Why:

* You cannot trust the system anymore
* Attackers may have hidden access (backdoors)
* Logs may be altered or incomplete

### Safe recovery approach:

* Wipe server completely
* Restore from a **trusted older backup**
* Rebuild system cleanly

---

# Attack Strategy: “The Long Game”

Advanced attackers often do not act immediately.

Instead, they:

* Quietly gain access
* Stay hidden for long periods
* Collect sensitive data slowly
* Avoid detection

### This makes detection difficult because:

* No obvious immediate damage
* Logs may look normal
* Activity is subtle and gradual

---

# Reading Authentication Logs

To inspect login attempts and system authentication:

```bash id="log1"
sudo cat /var/log/auth.log
```

---

## What this log shows:

* SSH login attempts
* Successful and failed logins
* Authentication events
* Security-related system activity

---

## Why it is useful:

* Detect unauthorized access attempts
* Monitor suspicious behavior
* Debug login issues

---

# One-Sentence Summary

**Server security relies on SSH keys instead of passwords, strict system controls like firewalls and updates, constant monitoring of authentication logs, and assuming that any compromised system must be fully rebuilt to stay safe.**
